## Context

The Go core is being developed separately. The user selected GL.iNet GL-E5800 NA Mudi 7 5G as the initial hardware candidate. Read-only SSH inspection observed GL.iNet 4.10.0, OpenWrt 23.05.4, aarch64 and procd; details and limitations are in `router-evidence.md`. The device has not been modified or lifecycle-tested, so this is not yet a supported installation target.

## Goals / Non-Goals

**Goals:** Persistent installation and supervised operation on at least one verified target; opt-in connected-client integration; reversible changes and operational visibility; preserving core protocol and security behavior.

**Non-Goals:** Implementing the core, changing the wire protocol, supporting every router or firmware, a GL.iNet GUI plugin, automatic firmware upgrades, and intercepting traffic types unsupported by the core.

## Decisions

1. **Target a verified firmware matrix, not a generic GL.iNet promise.** Identify a specific model, firmware version, CPU/ABI, init, firewall backend and available storage/RAM before implementation; document limitations and gate installation on detectable incompatibility. Build a matching Go binary and package it with install assets. A universal prebuilt image is rejected because firmware and architectures vary.
2. **Use the target's native persistent storage and service supervisor.** On a verified OpenWrt/procd target use a procd init script with respawn, controlled enable/disable, and bounded retry; adapt only after verification. Install config and credentials separately with restrictive permissions, preserve them on upgrade and ordinary removal, and do not hard-code CLI flags. A periodic cron watchdog is less integrated and less observable. Installation validates the configuration before enabling autostart.
3. **Separate service from opt-in traffic integration.** Use the core's documented transparent interception mode only if it actually exists and its supported protocols, readiness and failure behavior are known. Install a dedicated, identifiable firewall chain/hook or equivalent through the verified firmware's supported mechanism, scoped to explicitly selected client ingress and eligible traffic. Exclude router-originated upstream connections and other control/management traffic to prevent loops and lockout. Avoid modifying unrelated rules or assuming iptables vs nftables. A router-wide default redirect without scoping is unsafe.
4. **Fail open to normal routing, not silently insecure proxying.** The user chose this policy; the separate router-wide traffic change must be reconciled with that decision before traffic implementation. Attach interception only after a supported readiness check succeeds; detach it on stop, detected failure, disable or uninstall, and reconcile safely on reboot and firewall reload. When unavailable, packets use the router's preexisting routing and are not claimed to be protected by Starlight. If the platform cannot provide the required cleanup across crashes and reloads, do not advertise traffic integration as supported. This trades continuity of proxy use for management access; disclose direct-routing privacy implications before opt-in.
5. **Stage and recover changes.** Verify platform, artifact integrity, free space, configuration and prerequisites before mutation; stage the new binary, retain the previous executable and enabled state, and restore them after failed upgrade or startup validation. Manage only Starlight-owned files/rules, provide explicit purge for secrets and avoid changes to unrelated configuration. In-place overwrite without rollback is rejected.
6. **Deliver an opkg feed, not a GUI extension.** The inspected firmware has opkg and accepts `aarch64_cortex-a53`; construct an IPK for the qualified architecture with package-owned executable and init assets and appropriate configuration preservation, and publish a versioned HTTPS feed with `Packages`/`Packages.gz` metadata and package digest. Verify the exact GL.iNet Manage Sources input and UI discovery/install flow on the selected firmware rather than assuming it directly writes a particular file. Use authenticated feed metadata with a documented trust anchor; verify actual firmware's signature enforcement and key provisioning before release, without disabling checks. A direct binary download alone does not satisfy the user's requested workflow. Native opkg upgrades and removal must satisfy the rollback, config retention and traffic coordination requirements, not bypass them via maintainer scripts. If opkg's transaction semantics cannot meet those requirements, design and verify a compatible lifecycle before publishing.
7. **Prototype the client package without automatic activation.** The current client uses `client --host ... --port ...` and `SATMUX_PSK`, and has no standalone validation or readiness command. The local experimental IPK supplies an init script and a root-private config template, parses values without shell evaluation, and leaves service enablement to an operator. It does not claim the full installation or upgrade contract, publish a feed, alter firewall rules, or provide network-wide access. A compatible separately configured ground server and matching PSK are required. Production packaging remains blocked on integration contracts, authenticated feed, package lifecycle and on-device tests.

## Risks / Trade-offs

- [Core may lack transparent interception, readiness or needed protocol coverage] → Treat integration as blocked until agreed and tested; do not invent an API or silently fall back to a client proxy.
- [Fail-open allows direct traffic] → Explicit warning, documented coverage and outage behavior; never imply all traffic is tunneled or encrypted.
- [Crash, reboot or firewall reload leaves stale rules] → Verify supervisor/firewall ordering and cleanup on the selected firmware; test abrupt termination and reload on device, and block support if reconciliation cannot be guaranteed.
- [Flash/RAM constraints and respawn loops] → Measure binary size, storage, idle/loaded memory and CPU on target; avoid unbounded logs and frequent persistent writes, cap restart rate, document measurements and limitations.
- [Router access or vendor configuration disrupted] → Scope rules narrowly, preserve management and DNS behavior unless explicitly supported, offer local disable/recovery steps and test from an independent management path.
- [Secrets or supply-chain compromise] → Restrict config access, never log credentials, validate release integrity using a documented trusted verification method and avoid weakening core authentication or TLS.

## Migration Plan

For a fresh install, validate compatibility and integrity, stage files, configure and validate credentials, then enable/start the service. Traffic integration remains disabled until an explicit opt-in and readiness check. For upgrades, retain configuration and previous working binary; validate and atomically activate the staged version, verify startup, and restore the old version and prior enabled state on failure. For rollback, disable integration first, restore the prior binary and service state, and verify normal routing. Ordinary removal disables integration and service and removes owned artifacts while retaining configuration; an explicit purge removes retained credentials. Document recovery from console/SSH and limitations across firmware upgrades.

## Open Questions and Dependencies

- Can installation, service supervision, resource budgets and recovery be validated on the inspected device once router modifications are authorized? How will its model be identified reliably given the generic board identifier?
- What are the core's final build targets, configuration validation, invocation, credentials, transparent interception, supported traffic, upstream bypass, readiness and shutdown contracts? If missing, coordinate separately; this change must not assume their existence.
- What trusted release signing or checksum distribution mechanism exists? Which platform-specific persistence and firewall reload hooks are supported on the selected firmware?
- How does Manage Sources persist entries and refresh its package list on GL.iNet 4.10.0, and does this opkg build enforce signed indexes? How can users securely provision and rotate the feed trust key without weakening verification?

### Core coordination evidence

The currently observed client starts background ground-carrier attempts and returns from `NewClient` before an authenticated handshake. A running process or open loopback listener is therefore not a readiness check and cannot justify upgrade activation or rollback success. The package owner needs the core owners to confirm a side-effect-free configuration validation interface, authenticated carrier readiness/failure reporting, credential handling, lifecycle and resource-limit contracts; no interface is assumed from the current prototype. A separately provisioned ground server and matching PSK are required for end-to-end verification.
