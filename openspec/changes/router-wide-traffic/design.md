## Context

The initial target is GL.iNet GL-E5800 NA Mudi 7 5G. A router has been inspected read-only, but interception and recovery have not been tested on it. Upstream satmux exposes TCP-oriented proxies; it is not a general IP VPN. Core protocol and router distribution are being developed concurrently. The current `satmux.Client.Open` accepts a host and port but opens optimistically: success does not establish destination reachability. Its API and readiness semantics require coordination.

### Read-only target observations

- `ubus call system board`, `/etc/glversion` and `uname` report GL-E5800, GL.iNet firmware 4.10.0, OpenWrt 23.05.4 r24012-d8dd03c46f, kernel 5.15.170-perf and aarch64; `/etc/openwrt_release` reports `aarch64_cortex-a53` and `sdx75/generic`.
- `nft --version` reports 1.0.8; `iptables --version` reports 1.8.8 using nf_tables. `fw4` and `nft` are present. The live ruleset contains `inet fw4` with a destination-NAT prerouting hook, a flowtable and TCP/UDP flow offload; it also contains a separate `inet dns_table` redirecting TCP and UDP port 53 from `br-lan` to local DNS. Do not assume priority ordering between base chains at the same hook and priority. `fw4 print` emitted warnings about unrelated existing configuration; no changes were made.
- The live ruleset contains `inet filter` set `GL_DPI_BLOCK` with `flags timeout`. This shows that a timed set exists, not that the proposed lease syntax, renewal, expiration timing, or crash behavior has been validated. The live IPv4 LAN is `br-lan` at 192.168.8.1/24; Wi-Fi and cellular uplinks and multiple defaults exist. Interface names, subnets and uplinks are observations, not fixed defaults.

### Candidate crash-safe capture lease (unvalidated)

Investigate a separately owned nftables table and a timed set whose membership gates the LAN redirect rule. A healthy service would renew a short-lived element only after verifying listener and authenticated carrier health; process or health-monitor failure stops renewals, so the kernel expires it and new, not-yet-conntracked flows can use normal routing. Atomic nft transactions, hook priority ahead of conflicting NAT chains, exclusion of DNS/local/portal/ground destinations and firewall-reload reconciliation all need controlled tests. Select lease duration and health-detection bound from measurements; there is necessarily a window between failure and expiry, during which new flows can fail. NAT conntrack can retain an earlier redirect after lease expiry, so existing or same-tuple connections are not guaranteed to recover; do not flush unrelated conntrack state. The kernel timing/set semantics, crash behavior, offload interactions and survival across fw4 reload are unproven on this router. If they cannot be shown safe, do not enable capture. A direct socket from the relay is router-originated and can differ from normal forwarding in source address, firewall policy and accounting; removing capture is the preferred fail-open path for new flows.

## Goals / Non-Goals

**Goals:** Transparent IPv4 TCP for opted-in LAN clients; safe, observable policy; reversible integration on validated GL.iNet/OpenWrt targets; no per-client proxy configuration.

**Non-Goals:** New wire protocol, UDP/QUIC acceleration, transparent TLS interception, universal IPv6 tunneling, captive portal automation, a ground server implementation, or claiming that DNS is private.

## Decisions

1. **Destination-aware TCP adapter.** On a validated Linux/OpenWrt backend, redirect selected LAN IPv4 TCP to a local listener and recover the original destination using the kernel's original-destination facility. Pass address and port to an agreed core stream-opening interface. This preserves end-to-end application TLS and avoids reimplementing SOCKS or the carrier protocol. TPROXY/policy routing is an alternative if original-destination recovery or firewall behavior proves inadequate; select only after target tests. A core SOCKS interface is a fallback only if its destination and error semantics are agreed.
2. **Scope and routing policy.** Capture forwarded LAN traffic only, not router-originated traffic, and exclude router/local subnets, management, configured bypasses, and ground-server endpoints before interception. Default IPv4 TCP capture is opt-in; unsupported UDP (including QUIC), IPv6 and DNS follow existing router routes and are not protected by Starlight. DNS answers may be local/intercepted and only IP destinations are available; no remote DNS guarantee. Explicit bypass enables captive-portal access. Alternatives such as blocking UDP or pretending it is tunneled would change connectivity unexpectedly.
3. **Failure policy.** User-selected fail-open: when service or ground server is unavailable, new connections use normal direct routing. An intercepted connection may be dialed directly if a core open fails before any bytes are forwarded; existing streams are never replayed and can fail. Optimistic `Open` cannot identify later ground or destination failure, so it alone is not a health check. Detect carrier failure separately and disable capture; bound detection time and disclose transition gaps after backend testing. Report fallback prominently: this is not a privacy boundary. Direct routing may still be blocked by the network.
4. **Lifecycle and privilege.** A privileged router integration installs narrowly scoped, identifiable firewall rules only after listener and core readiness; stop/disable removes only owned rules. Fail-open on process crash requires an independent mechanism (for example, a verified expiring firewall lease), not merely cleanup in the process that might crash. Validate prerequisites before mutation, use atomic updates where backend supports them, and reconcile owned state after crashes, restarts, firewall reloads and reboot. If safe expiry cannot be demonstrated, do not enable capture. Never flush or rewrite unrelated firewall state. A persistent service/package is coordinated with deployment work, not independently designed here.
5. **Bounded operation.** Enforce configurable finite connection and buffering limits, timeout idle/failed connections, expose readiness, policy and counters without logging payloads or secrets. Reject excess flows rather than exhausting the router. Limits and target firmware are validated before support is declared.

The standalone `routertraffic` package now provides a caller-owned listener, Linux IPv4 `SO_ORIGINAL_DST` lookup, configurable connection/lifetime limits and counters, and an adapter to the current `satmux.Client.Open` interface. A local test exercises the listener through the Go core and ground server with an injected destination; the Linux lookup has been cross-compiled but has not been exercised against target NAT. Its fallback handles only an error returned before stream creation; it cannot detect ground unavailability after an optimistic open. The separate `starlight-router-lab` executable binds only to numeric loopback, uses a fixed target, and never configures firewall rules. It is a local relay test tool, not router-wide interception.

`RunLease` is an injectable coordinator that renews only after a successful health callback and revokes on unhealthy checks and shutdown; renewal failure terminates the coordinator and attempts revocation. `ProbeGround` opens a fresh carrier, authenticates and verifies a matching ping/pong with a deadline. This is not a check of the actual client pool, local listener or forwarding path and must be combined with those checks before any lease can be renewed. An experimental nft updater submits a single transaction to flush and add a timed interface element in a pre-existing dedicated set; it does not create rules, establish ownership, or activate capture. Its transaction/cancellation and expiration behavior are unverified and it must not be used for capture: in particular a canceled nft process may leave an ambiguous kernel transaction outcome. Its deliberately distinct method names prevent it from satisfying the coordinator's lease interface. Unit tests mock the nft runner, not a real expiring firewall rule. The lease contract requires independent expiry and no delayed updates after cancellation. No validated production backend, complete health check, live status integration, or activation wiring is supplied. Core owners have not confirmed the interface contract and hardware/coordination gates remain open.

Management-access protection is a prerequisite to any deployment experiment: discover all current router-owned addresses and management networks, verify exclusions are applied before any redirect and cannot be shadowed by another base chain, preserve an independent recovery path, and establish a tested rollback that does not rely on the service process. Do not assume the currently observed LAN address, DNS chain ordering, or that all GL.iNet client interfaces remain unchanged. None of these safeguards has been verified on the router; no activation is implemented.

The main client now has an experimental, disabled-by-default `--transparent-port` listener using the existing core client and Linux original-destination lookup. The experimental OpenWrt service accepts a matching `transparent_port` configuration, disabled by default. Neither installs firewall rules or performs health-gated capture. The listener binds all IPv4 interfaces when enabled; direct-connection rejection is not a substitute for firewall access controls. Do not enable it on the router until capture, exclusions, and failure handling are validated.

An isolated on-device nftables experiment created a temporary table with no hooks or rules, inserted a `br-lan` interface element with a two-second timeout, observed the element present and then absent after four seconds, and removed the table. This supports basic timed-set expiry on this firmware; it does not validate capture, timing bounds, renewal races, crash/reload behavior, or management safety.

`CaptureHealth` combines a local TCP check of the actual relay listening socket with an injected client-pool probe such as `Client.Probe`. It requires a deadline and restricts the listener check to numeric loopback. It is not yet wired to a firewall lease or service and does not prove the forwarding path or firewall health; a successful check is only point-in-time evidence.

An experimental nft policy generator creates an exclusively owned table with a NAT prerouting chain, LAN interface match, empty timed lease, local/DNS and configured IPv4 destination exclusions. On the GL-E5800 the proposed policy passed `nft -c`, was installed with an empty lease, inspected and removed. A second temporary NAT chain restricted to a verified nonexistent interface accepted a two-second lease and showed its expiry while the chain existed. Both tables were removed. Neither test redirected live traffic or demonstrates original destination recovery, actual LAN forwarding, service integration, crash/reload safety, or suitable exclusions for every router topology.

Subsequently integrated experimental capture with the client, procd service and OUI RPC. On GL-E5800 firmware 4.10.0, a connected client made an IPv4 HTTPS request whose observed public egress was the Go ground server. With the ground server deliberately stopped, a new request after 20 seconds used the normal uplink; after the server restarted, a new request used the ground server again. An initial outage revealed a typed-nil stream panic and stale-table restart failure; both were corrected before repeating the successful outage test. The OUI RPC disabled capture and removed the dedicated table, then re-enabled it. Capture was left enabled. This is an experimental live deployment, not a complete validation: other client types, sustained load, explicit crash/reboot/firewall-reload recovery, all bypasses, and OUI browser switch behavior remain unverified. New IPv4 TCP connections may fail during the lease-expiry window; UDP, IPv6 and DNS are not captured. Router changes were copied outside the installed opkg package.

A subsequent physical router reboot was confirmed by a changed boot ID. After reboot the client was enabled and running, router-wide capture was enabled and active, the authenticated ground connectivity probe passed, and a connected client's IPv4 HTTPS request again reported the ground server as its egress. The OUI menu and view files remained present. This single reboot does not validate crash or firewall-reload recovery, upgrades, or sustained operation.

## Risks / Trade-offs

- [Traffic leaks through unsupported protocols or local DNS] → Explicitly surface direct-routing scope and do not market as VPN/privacy protection.
- [Crash leaves stale interception] → Require independently expiring capture or an independently verified cleanup mechanism; target support is gated on outage and crash tests.
- [Direct fallback exposes traffic] → Explicitly disclose and report fallback; never present this feature as a VPN or privacy guarantee.
- [Capture loops or inaccessible portal/router] → Forwarded-LAN-only matching plus endpoint/local exclusions and operator-controlled bypass.
- [Core stream interface changes or differs from upstream] → Jointly agree destination, readiness, close/error, resource and security semantics; block integration until contract is stable and interoperability tested.
- [Hardware/firmware variants differ] → Declare supported firmware, firewall backend and device resource limits only after on-device validation; fail without changes on unsupported platforms.

## Migration Plan

Install with interception disabled. Validate router/backend and core configuration, authenticate the captive portal as needed, then opt in and verify status and LAN connectivity. Persist only explicit enablement across service/router restarts. Disable removes owned state and restores prior routing; uninstall also cleans owned state without altering unrelated rules. Document recovery from an interrupted enable and rollback to direct routing.

## Open Questions

- Does the observed GL-E5800 firmware support the proposed timed lease and reliable renewal/expiry under crash and firewall reload? Determine IPv6 topology and repeat evidence on any other supported firmware.
- What core stream API and readiness/failure semantics will core owners commit to, including handling IP destinations and compatibility with the upstream ground server?
- Which service/package owns startup ordering, privilege separation, firewall reload hooks, and persistence? Coordinate with deployment and cross-platform release owners.
- What operational connection, buffer and timeout defaults fit the chosen router under measured load?
